# SoDEX Farming Doctrine

Last updated: 2026-06-09

This document records the user's operating doctrine for the SoDEX farming
project. It overrides interpretations that treat SoDEX farming as a pure
capital-protection or profit-only trading bot.

## Primary Target

The minimum weekly transaction-volume target is:

- **$1,300,000 weekly SoDEX transaction volume**

All planning, execution, sizing, and risk controls must be evaluated on a
weekly basis against this target.

## Core Principle

The project goal is to farm SoPoints by generating large weekly transaction
volume on SoDEX. The intended way to make that sustainable is:

1. Predict the market direction of selected crypto assets accurately.
2. Place SoDEX transactions in the predicted direction or structure.
3. Use trading profit to cover the fees and transaction costs generated by the
   farming activity.
4. Maintain weekly performance good enough that volume generation does not
   become uncontrolled fee burn.

SoDEX farming is therefore not only a "never trade unless fee-free" system. It
is a weekly target-seeking farming engine where directional accuracy, realized
P&L, fees, volume, and win rate must be managed together.

## Weekly Success Metrics

The minimum weekly metrics are:

- **Weekly volume:** at least `$1,300,000`
- **Total Real Ratio:** minimum `1:9,100`; maximum target is **no net loss**
  while reaching the weekly trading-volume target — E1 profit must cover all
  volume-generation costs (E1 + E2 fees), and E2 directional losses must be
  minimized through precise, correct market-direction determination on SoDEX
- **Weekly profitable transaction ratio:** above `69%`
- **Weekly cost coverage:** fees and transaction costs should be covered by
  trading profit as much as possible

Total Real Ratio must be calculated from SoDEX official credited volume, not
only the internal ledger. The internal ledger remains an audit source, but the
official SoDEX dashboard is canonical for SoPoints/credited-volume progress.

The operating model is:

- **E1 = profit engine:** spot/wide-spread maker capture and inventory discipline
  should generate enough realized profit to cover E2 costs.
- **E2 = volume engine:** perps/futures volume generation should be scaled only
  when E1 profit coverage and maker efficiency keep the combined Total Real
  Ratio inside the target band.
- **Gross ratio:** official credited volume divided by fees.
- **Net ratio:** official credited volume divided by `fees - E1 realized
  profit`, floored at zero. The minimum target is `1:9,100`; the maximum target
  is **no net loss** — E1 realized profit must cover all volume-generation costs
  (E1 fees + E2 fees), and E2 directional losses must be minimized through
  precise market-direction prediction. This is the No-Loss Guarantee:
  `E1_realized_profit ≥ total_fees_E1 + total_fees_E2`.
- **E1 subsidy formula:** `required E1 profit = max(0, gross cost -
  official credited volume / 9100)`.

Planned capital support, when explicitly provided by the user, may be modeled as
separate lanes:

- **Spot/E1 additional capital:** `$100`
- **Perp/Future/E2 additional capital:** `$150`

The target win-rate threshold is explicitly a weekly target. Isolated single
trades or isolated daily variance should not dominate the decision unless they
threaten the weekly risk budget or show a clear execution failure.

## Method Mandate

The agent's task is to find and implement the most suitable methods to reach the
weekly targets above. Candidate methods include, but are not limited to:

- Directional prediction of crypto assets before SoDEX execution
- Pre Top Gainer / Pre Top Loser discovery: find SoDEX-listed crypto assets
  before they experience a sharp rise or sharp drop
- Pre-Gain / Pre-Loser scanning and validation
- SoSoValue Top Gainer / Top Loser data integration, mapped against assets
  available on sodex.com
- Anantara Sakti Pre-Sentiment system integration
- Anantara Sakti intelligence system integration
- Anantara Sakti Top Pre-Gain-Loser Scan & Trading System integration,
  adapted to SoDEX market structure
- Market-regime filtering
- SoDEX spot and perps route selection
- Dynamic sizing based on weekly progress
- Fee-aware execution
- Profit/cost tracking at weekly granularity
- Adaptive mode selection between strict, balanced, farming, and catch-up modes

The system should be flexible enough to keep progressing toward the weekly
volume target, while still preventing reckless execution, stuck positions,
unbounded fee burn, stale data usage, or unsafe deprecated execution paths.

## Implementation Implication

Future changes should avoid a binary interpretation of:

> "Only trade when every roundtrip is guaranteed positive after fees."

The correct interpretation is:

> "Find a repeatable weekly method where accurate market prediction and
> disciplined execution generate enough profit to cover SoDEX transaction costs
> while reaching at least $1.3M weekly volume and more than 69% profitable
> transactions."

## User-Recommended Discovery Method

The user specifically recommends that the SoDEX farming project focus on
discovering assets before they become **Top Gainers** or **Top Losers**.

The intended workflow is:

1. Use SoSoValue ecosystem data for updated Top Gainer and Top Loser lists.
2. Map those assets to the tradable universe available on sodex.com.
3. Detect early signs of sharp upward or downward moves before the move becomes
   obvious in the Top Gainer / Top Loser table.
4. Use Anantara Sakti's existing Pre-Sentiment system and intelligence system as
   confirmation layers.
5. Integrate and adapt the existing Anantara Sakti Top Pre-Gain-Loser Scan &
   Trading System to SoDEX-specific market conditions, fees, spreads, liquidity,
   and execution constraints.
6. Execute SoDEX farming/trading only through the guarded SoDEX route selection
   and weekly target framework.

This method should be treated as a primary research and implementation path for
reaching the weekly $1.3M volume target with more than 69% profitable
transactions.

## Continuous Improvement Obligation

The agent is required to operate in a continuous learning and improvement loop
at all times while working on the SoDEX farming project:

> **Belajar → Belajar → Belajar → Riset → Analisa → Review → Perbaikan →
> Improve → Verifikasi → Ulangi**

This means:

- keep learning from repo context, market data, outcomes, tests, logs, and user
  corrections;
- keep researching current SoSoValue/SoDEX/Anantara evidence when decisions
  depend on fresh market state;
- keep analyzing weekly progress against the $1.3M volume and >69% profitable
  transaction targets;
- keep reviewing assumptions, stale logic, unsafe paths, execution quality, and
  mismatches with the user doctrine;
- keep repairing bugs, documentation drift, and operational risk;
- keep improving prediction, scanner quality, sizing, route selection, latency,
  and weekly target management.

This loop is mandatory and ongoing. The project should not be treated as a
one-time implementation task.

Required skill usage by work type:

- **Research and source mapping:** use `research-ops` when working with current
  SoSoValue data, SoDEX market availability, Top Gainer / Top Loser lists, and
  recurring public-data monitoring. Separate sourced facts, local evidence,
  inference, and recommendation.
- **Implementation and bug fixing:** use `tdd-workflow` for scanner, routing,
  policy, sizing, execution, and state-tracking changes. Add or update tests
  before production code whenever practical, then verify with the focused test
  target and full quality gate.
- **Live-order, key, and execution safety:** use `security-review` whenever code
  touches SoDEX CLI calls, environment secrets, signed orders, subprocesses,
  Telegram commands, or any route that can create/cancel orders.
- **Fresh market detection and execution timing:** use
  `latency-critical-systems` for Pre Top Gainer / Pre Top Loser scanning,
  SoSoValue/SoDEX polling, orderbook freshness, queue depth, stale cache
  detection, and fast mode switching.

The intended workflow for new SoDEX farming capability is:

1. Research the target signal and data source with `research-ops`.
2. Define weekly success/failure metrics against the $1.3M and 69% targets.
3. Add focused tests with `tdd-workflow`.
4. Implement the smallest safe scanner/policy/execution change.
5. Review live-order and secret surfaces with `security-review`.
6. Measure freshness and hot-path timing with `latency-critical-systems`.
7. Run the focused tests, full unit suite, and project audit before treating the
   change as ready.
